## 그룹 2. 구조 · 설계 설명

### Q6. 이중 연결 리스트의 노드 구조(prev, next, data)와 핵심 메서드들이 O(1)로 동작하도록 어떻게 구성했는가?

**모범답변 포인트**:
- 노드: `data`(여기선 key) + `prev` + `next` 두 방향 포인터
- head/tail 더미(dummy) 노드를 두면 첫/마지막 삽입·삭제가 경계 예외 없이 항상 같은 코드로 처리됨
- `insert_front`, `remove_front`, `remove_back`, `remove_node`, `move_to_front` 모두 포인터 몇 개만 바꾸면 끝 → 순회 없이 O(1)
- `remove_node`가 O(1)이 되려면 **노드를 미리 알아야** 하는데, 그 노드 참조를 해시맵이 들고 있음 (→ Q10과 연결)

**꼬리질문 추천**: "단일 연결 리스트로는 왜 안 되나요?" → remove_node 시 prev를 찾으려면 O(n) 순회 필요. prev 포인터 때문에 이중이 필수라는 답이 나와야 함.

- [ ] 통과

### Q7. 해시 함수가 어떤 입력을 받아 어떤 과정을 거쳐 인덱스를 만드는가?

**모범답변 포인트** (본 프로젝트 기준 예시):
- 입력: 문자열 키 → UTF-8 바이트 변환
- 과정: 각 바이트에 소수(예: 31) 기반 다항식 롤링 (`h = h*31 + byte`) → 큰 정수 하나 생성
- 인덱스: `h % 버킷_개수`로 버킷 배열 범위 안으로 압축(modulo)
- 소수를 곱하는 이유: 자릿수 정보가 살아나 균등하게 퍼짐

**꼬리질문 추천**: "그냥 글자 코드 다 더하면 왜 안 좋나요?" → 순서가 달라도 합이 같아 충돌 몰림(ab/ba 같은 경우).

- [ ] 통과

### Q8. 충돌 해결을 체이닝 방식으로 어떻게 구현했는가? (버킷 내부 구조 선택 포함)

**모범답변 포인트**:
- 버킷 = 고정 길이 배열(list). 각 칸에 연결구조 하나
- 서로 다른 키가 같은 인덱스에 가면 그 칸 **안에 여러 엔트리를 연결**(체이닝)해서共存
- 본 프로젝트: 버킷 내부를 **직접 만든 이중 연결 리스트로 재사용** → 코드 재사용 + remove_node O(1)
- 탐색은 그 칸만 순회 → 평균적으로 칸에 담긴 개수(=로드팩터)개만 비교

**꼬리질문 추천**: "버킷 안을 list로 해도 되잖아요?" → 되지만 중간 삭제가 O(n). DLL이면 O(1).

- [ ] 통과

### Q9. 로드 팩터 0.75 초과 시 "버킷 2배 확장"을 어떤 절차로 수행하는가?

**모범답변 절차**:
1. put 후 `size / bucket_count > 0.75` 확인
2. 새 버킷 배열을 **2배 크기로 생성**
3. 기존 모든 엔트리를 순회하며 **새 해시 인덱스를 다시 계산(rehash)** 해 새 배열에 삽입 (버킷 수가 바뀌었으므로 `% bucket_count` 결과가 달라짐)
4. 기존 배열 버림

**꼬리질문 추천**: "확장 비용은 얼마인가요?" → O(n)이라 순간 부하. 하지만 n개 넣는 동안 총 확장 비용을 나누면 평균(상각) O(1)이라는 개념까지 나오면 만점.

- [ ] 통과

## 그룹 3. 원리 이해 · 근거 설명

### Q10. LRU 구현에서 "해시맵 + 이중 연결 리스트"가 각각 어떤 역할을 하고, 왜 둘 다 필요한가?

**모범답변 포인트**:
- 해시맵: key → (값 + DLL 노드 참조) 매핑. **찾기**를 O(1)로
- 이중 연결 리스트: 노드들을 "최근 사용 순서"로 줄 세움. **순서 갱신**을 O(1)로 (move_to_front)
- 둘 다 필요한 이유: 해시맵만 있으면 순서를 모르고(제거 대상 찾으려면 전체 순회), DLL만 있으면 key로 노드를 못 찾음(O(n)). **각자의 약점을 서로가 보완**

- [ ] 통과

### Q11. O(1) LRU 원리를 "조회(해시) + 갱신(리스트 이동)" 관점에서 설명할 수 있는가?

**모범답변 흐름** (GET 하나로 설명하게):
1. 해시맵에서 key로 노드를 즉시 조회 — O(1)
2. 그 노드를 리스트 맨 앞으로 옮김(move_to_front, 포인터 4개 변경) — O(1)
3. 값 반환
- 어느 단계에도 전체 순회가 없으므로 조회든 갱신이든 항상 O(1)

**꼬리질문 추천**: "노드 위치를 어떻게 바로 알죠?" → 해시맵이 노드 객체 참조를 저장하고 있기 때문. Q10과 일관되게 답하는지 확인.

- [ ] 통과

### Q12. TTL 관리에 힙을 사용한 이유(가장 빠른 만료를 빠르게 찾는 성질)를 설명할 수 있는가?

**모범답변 포인트**:
- 최소 힙: (expire_at, key)를 넣으면 **가장 만료가 빠른 항목이 항상 꼭대기**
- peek O(1)로 다음 만료 확인, push/pop O(log n)
- 리스트로 하면 "다음 만료 찾기"가 O(n) 정렬/순회 필요 → 힙이 적중
- 실제 만료 처리는 조회 시점에 "지금 시간과 비교해 과거면 삭제"하는 방식(lazy expiration)으로 동작

- [ ] 통과

### Q13. 메모리 초과 시 eviction 흐름을 단계별로 설명할 수 있는가? (used_memory 산정/갱신, LRU 제거, evicted_keys 증가 포함)

**모범답변 흐름** (SET 하나로):
1. 새 엔트리 크기 = len(utf8(key)) + len(utf8(value)) 계산
2. used_memory에 더하기 전/후로 한도 초과 판단 (단일 엔트리가 한도보다 크면 OOM 에러)
3. 초과하는 동안 while 반복: DLL **맨 뒤(가장 오래된) 노드**를 꺼냄 → 해시맵에서 해당 key 삭제(+TTL 정리) → used_memory에서 그 엔트리 크기 차감 → evicted_keys += 1
4. used_memory ≤ maxmemory가 되면 저장 허용

- [ ] 통과

### Q14. GET 명령어 전체 흐름을 순서대로 설명할 수 있는가? (TTL 확인 → 삭제 여부 → 값 반환 → LRU 갱신 조건)

**모범답변 순서**:
1. 해시맵에 key 있는지 확인 → 없으면 `(nil)`
2. 있으면 TTL 검사: expire_at ≤ 지금이면 **삭제 후** `(nil)` (이때는 LRU 갱신 안 함 — 죽은 키를 "최근 사용"으로 올리면 안 되므로)
3. 살아있으면 값 반환 + **이 경우에만** move_to_front로 LRU 갱신

**꼬리질문 추천**: "만료 삭제인데 LRU를 갱신하면 뭐가 문제죠?" → 사용하지도 않은 키의 recency가 올라가 LRU 우선순위가 오염됨.

- [ ] 통과

## 그룹 4. 확장 · 응용 질문

### Q15. LRU 대신 LFU 정책을 구현한다면 자료구조를 어떻게 변경해야 하는가?

**모범답변 포인트**:
- LFU는 "사용 횟수" 순서라서 단일 DLL 한 줄로는 불가 (횟수별 줄이 필요)
- 변경안: 해시맵은 유지(key → 값+freq+노드), DLL을 **빈도별 버킷**(freq → DLL)으로 교체하고, 최소 freq 버킷을 O(1)에 찾기 위한 포인터 추가
- 접근할 때마다 freq+1 후 상위 빈도 버킷으로 노드 이동 — 여전히 O(1) 유지 가능
- "LRU는 시간순 한 줄, LFU는 횟수순 여러 줄"로 요약하면 좋음

- [ ] 통과

### Q16. 데이터가 10만 건으로 늘어나면 현재 구조에서 병목이 될 수 있는 부분은 어디이며, 어떻게 개선할 수 있는가?

**모범답변 포인트**:
- rehash: 버킷 2배 확장 시 순간 O(n) → 미리 크기를 예측해 초기 용량을 크게 잡거나, 점진적(incremental) rehash로 나눠 처리
- TTL 힙: 키가 DEL/덮어쓰기 돼도 힙 속 오래된 항목이 남아 누적 → lazy 삭제 조건 강화 또는 정기 청소
- KEYS/DBSIZE 같은 전체 순회 명령은 여전히 O(n) → 실제 Redis처럼 스캔 분할 등 고려
- 평균 연산(SET/GET)은 로드팩터 관리 덕분에 여전히 O(1)이라는 점을 구분해 말하면 좋음

- [ ] 통과

### Q17. used_memory에 자료구조 오버헤드까지 포함하는 모델로 바꾸면 무엇이 달라지고, 공정한 비교/채점을 위해 어떤 보정이 필요한가?

**모범답변 포인트**:
- 현재 모델: 키+값 문자열 길이만 합산 → 구현 디테일과 무관하게 공정하지만 실제 메모리보다 적게 셈
- 오버헤드 포함 시: 노드 객체(prev/next/포인터), 버킷 배열 슬롯, 힙 요소까지 더해져 eviction이 훨씬 일찍 발생 → 같은 maxmemory에서 저장 가능한 키 수가 구현마다 달라짐
- 보정: 채점용으로는 "무엇을 셀지"를 명세로 고정해야 비교 가능. 파이썬은 sys.getsizeof 등으로 측정하지만 언어/버전마다 달라지므로, 채점 규격에는 단순 공식(현행)이 오히려 공정하다는 논지까지 나오면 만점

- [ ] 통과
