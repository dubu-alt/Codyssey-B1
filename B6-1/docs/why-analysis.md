# WHY 분석 — AWS 클라우드 인프라 구축 과제

## 1. 왜 이 문제인가 (목적)

이 과제의 핵심 목적은 **"클라우드는 단순히 빠른 컴퓨터가 아니라, 네트워크·보안·권한이 유기적으로 결합된 환경"**이라는 사실을 체득하는 것이다.

현업에서 가장 흔한 사고는 "서버에 올렸는데 외부에서 접속이 안 된다"는 상황이다. 이 문제를 겪고 직접 해결하려면 VPC 네트워크 구조, 보안 그룹, 라우팅, IAM 권한을 **통합적으로** 이해해야 한다. 단편적 지식이 아닌 **연결된 사고력**을 기르는 것이 이 과제의 존재 이유다.

## 2. 왜 AWS인가 (기술 선택)

| 비교 항목 | AWS | GCP | Azure |
|----------|-----|-----|-------|
| 프리 티어 범위 | EC2 t2.micro 12개월 무료 | e2-micro 상시 무료 | B1s 12개월 무료 |
| VPC 설계 자유도 | 높음 (Subnet, RT, IGW 개별 제어) | 자동 모드 존재로 학습 효과 낮음 | 유사하나 용어 상이 |
| 시장 점유율 | 1위 (약 31%) | 3위 | 2위 |
| 학습 자료 | 가장 풍부 | 중간 | 중간 |

**선택 근거**: AWS는 VPC 내 모든 구성요소(Subnet, Route Table, IGW)를 수동으로 제어해야 하므로 네트워크 설계를 **강제로** 학습하게 된다. GCP의 auto-mode VPC처럼 자동 설정이 없어, 각 구성요소의 역할을 직접 이해해야만 동작하는 환경이다.

## 3. 왜 이 구조인가 (아키텍처 설계 근거)

### 3.1 단일 VPC + 단일 Public Subnet 구조

**선택**: VPC 1개, Public Subnet 1개 (AZ 1개)

**이유**:
- 이 과제는 **네트워크 기초 이해**가 목표이므로, Multi-AZ나 Private Subnet은 복잡도만 높이고 학습 효과를 희석시킨다
- 단일 Subnet에서 외부 트래픽이 EC2까지 도달하는 **전체 경로**(IGW → Route Table → Subnet → SG → EC2)를 명확히 추적 가능
- Private Subnet + NAT Gateway는 비용 발생(시간당 $0.045 + 데이터 전송 비용)으로 프리 티어 범위 초과

### 3.2 Internet Gateway 연결

**필수 이유**: IGW 없이는 VPC 내부에서 외부 인터넷 통신이 불가능하다. VPC는 기본적으로 **격리된 네트워크**이므로, 외부와의 통신 게이트를 명시적으로 연결해야 한다.

### 3.3 Route Table에 0.0.0.0/0 → IGW 경로

**필수 이유**: Subnet이 IGW를 통해 외부와 통신하려면 Route Table에 기본 경로(default route)가 있어야 한다. 이 경로가 없으면 외부 요청은 VPC 내부에서만 순환하고 인터넷에 도달하지 못한다.

### 3.4 Security Group 설계 (최소 권한)

| 포트 | 프로토콜 | 소스 | 선택 이유 |
|------|---------|------|----------|
| 80 | HTTP | 0.0.0.0/0 | 웹 서비스는 누구나 접근 가능해야 하므로 전체 개방 |
| 22 | SSH | 개인 IP/32 | SSH는 관리용이므로 학습자 IP만 허용. 전체 개방 시 brute-force 공격 노출 |

**금지 사항**: 0-65535 전체 포트 개방은 불필요한 서비스 노출로 공격 표면(attack surface)을 극대화하므로 절대 금지.

### 3.5 IAM 최소 권한 원칙

**선택**: EC2/VPC/SG 관련 작업만 허용하는 커스텀 IAM 정책

**이유**:
- AdministratorAccess는 모든 AWS 서비스에 대한 전체 권한을 부여하여, 실수로 S3 버킷 공개, RDS 삭제 등 치명적 사고 가능
- 실습에 필요한 서비스(EC2, VPC, SG)만 허용하면 실수의 영향 범위가 제한됨
- 현업에서 IAM 정책은 "필요한 것만 허용"이 원칙이며, 이 습관을 처음부터 들여야 함

## 4. 왜 Nginx인가 (웹 서버 선택)

| 비교 항목 | Nginx | Apache | Node.js (Express) |
|----------|-------|--------|-------------------|
| 메모리 사용량 | 매우 낮음 (~2MB) | 높음 (~10MB+) | 중간 |
| t2.micro 적합성 | 최적 | 무거움 | 적합 |
| 설치 복잡도 | `apt install nginx` 한 줄 | 유사 | Node 런타임 필요 |
| 정적 페이지 서빙 | 최적화됨 | 가능 | 과도한 설정 |
| 헬스체크 구성 | location 블록 추가로 간단 | .htaccess 또는 conf | 코드 작성 필요 |

**선택 근거**: t2.micro (메모리 1GB)에서 가장 가볍게 동작하며, 설치와 설정이 단순하고, `/health` 엔드포인트 구성도 Nginx 설정 파일 한 줄로 가능하다.

## 5. 왜 옵션 B(헬스체크)를 선택했는가

**선택**: `GET /health → 200 OK, "OK"` 방식

**이유**:
- 브라우저 접속(옵션 A)은 육안 확인에 의존하여 자동화 검증이 불가능
- 헬스체크 API는 `curl -s -o /dev/null -w "%{http_code}"` 명령으로 **프로그래밍적 검증** 가능
- 현업에서 Load Balancer(ALB)의 Target Group 헬스체크, 모니터링 시스템(CloudWatch, Datadog)은 모두 헬스체크 엔드포인트 기반으로 동작
- 운영 환경에서 필수적으로 사용되는 패턴을 미리 학습하는 효과

## 6. 왜 이 트러블슈팅 방법론인가

**"가설 → 검증" 순서를 유지하는 이유**:

무작정 설정을 바꾸는 것은 **문제를 더 복잡하게** 만든다. 증상을 관찰하고, 가능한 원인을 가설로 세우고, 하나씩 검증하면:
- 변경 사항을 추적할 수 있어 **롤백이 가능**
- 근본 원인(root cause)을 찾을 수 있어 **재발 방지** 가능
- 로그와 증거 기반이므로 **팀 내 공유 및 문서화** 가능

## 7. 왜 리소스 정리가 중요한가

AWS 과금은 **리소스가 존재하는 것만으로** 발생할 수 있다:
- Elastic IP: 인스턴스에 연결되지 않은 상태로 방치 시 시간당 과금
- EBS 볼륨: EC2 종료 후에도 별도 삭제하지 않으면 GB당 월 과금
- NAT Gateway: 시간당 $0.045 + 데이터 전송 비용

따라서 실습 종료 후 **체크리스트 기반 순서대로** 삭제해야 하며, 최종적으로 Billing Dashboard에서 확인하는 것이 필수다.
