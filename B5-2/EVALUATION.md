### 시연 스크립트 (그룹 1 확인용)

```text
python -m mini_git.main
mini-git> INIT Alice                       -> 저장소 초기화, main 브랜치 + HEAD + 사용자 설정
mini-git> COMMIT "Add login feature"       -> hash 출력
mini-git> COMMIT "Fix login bug"
mini-git> LOG                              -> 부모(오래된 커밋)가 자식보다 먼저 출력
mini-git> BRANCH feature                   -> 브랜치 생성
mini-git> SWITCH feature                   -> HEAD 전환
mini-git> COMMIT "Add logout"              -> 이 커밋은 feature에 붙음
mini-git> LOG                              -> 분기 후 순서 확인
mini-git> PATH <hash1> <hash2>             -> 최단 경로 출력
mini-git> PATH <hash1> 없는hash            -> No path
mini-git> ANCESTORS <hash>                 -> 모든 조상 출력
mini-git> SEARCH login                     -> 키워드 검색
mini-git> SEARCH --author=Alice            -> 작성자 검색
mini-git> LOG --sort-by=date               -> 직접 만든 정렬로 재정렬
mini-git> LOG --sort-by=author
```

**주의**: 데이터는 메모리 전용이라 프로그램을 종료하면 사라짐 → **한 세션 안에서** 시연 스크립트를 전부 진행해야 합니다.

## 그룹 1. 결과물 · 기능 요구사항 확인

### Q1. INIT 실행 후 main 브랜치 / HEAD / 현재 사용자 설정이 정상적으로 초기화되어 있는가?

**확인 방법**: INIT 후 첫 COMMIT의 author가 설정한 사용자명인지 LOG에서 확인. main 브랜치 존재도 SWITCH main으로 확인 가능.

- [ ] 확인 완료

### Q2. BRANCH 생성 후 SWITCH로 전환되며, 이후 COMMIT이 해당 브랜치에 반영되는가?

**확인 방법**: 브랜치 생성 → switch → commit → log. 새 커밋이 갈라져 나온 것(분기)이 보여야 함. 원래 브랜치의 log에는 새 커밋이 없어야 함.

- [ ] 확인 완료

### Q3. LOG가 "부모 커밋이 자식 커밋보다 먼저" 출력되는가?

**확인 방법**: 커밋 3개 이상 쌓은 상태에서 LOG. 오래된 커밋(조상)이 항상 아래에서 위로든 위에서 아래든 **자식보다 먼저** 나와야 함. 분기가 있어도 조건이 깨지면 실패.

- [ ] 확인 완료

### Q4. PATH <a> <b>가 경로가 있으면 최단 경로를, 없으면 No path를 출력하는가?

**모범 규칙**: 간선 수 최소 경로 + 경로가 여러 개면 사전순 최소. 분기된 두 커밋 사이는 공통 조상을 거쳐 연결됨(무방향).

- [ ] 확인 완료

### Q5. ANCESTORS <hash>가 모든 조상을 빠짐없이 출력하는가?

**확인 방법**: merge 상황처럼 부모가 둘인 구조를 만들 수 있다면 가장 좋고, 아니면 분기 전 커밋들의 조상이 전부 나오는지 확인. 하나라도 빠지면 실패.

- [ ] 확인 완료

### Q6. SEARCH <keyword> / SEARCH --author=<name> / LOG --sort-by=date|author가 요구사항대로 동작하는가?

**확인 포인트**:
- SEARCH: 메시지 단어 일치로 커밋 즉시 검색 (전체 순회 방식이면 감점 — Q13에서 설명 확인)
- --sort-by=date: timestamp 기준, --sort-by=author: 작성자 기준. **직접 구현한 정렬**(merge sort)로 처리했는지 코드로 확인

- [ ] 확인 완료

## 그룹 2. 구조 · 설계 설명

### Q7. 커밋 저장소 / 브랜치 / HEAD / 사용자 정보를 어떤 구조로 분리했고, 각 책임을 설명할 수 있는가?

**모범답변 포인트**:
- 커밋 저장소: hash → Commit 객체 매핑(graph.py). 커밋 자체의 보관소
- 브랜치: 브랜치 이름 → 커밋 hash 포인터 목록. "특정 커밋을 가리키는 이름표"
- HEAD: 지금 작업 중인 위치(브랜치 이름 또는 커밋) 하나만 가리킴
- 사용자 정보: 현재 author 문자열
- 분리 이유: 커밋 그래프는 불변 데이터, 브랜치/HEAD는 움직이는 포인터 — 성격이 다른 걸 섞으면 switch 로직이 꼬임

- [ ] 통과

### Q8. 커밋 hash로 빠르게 조회하기 위해 어떤 키-값 구조를 사용했고, 중복/충돌을 어떻게 방지했는가?

**모범답변 포인트**:
- dict(해시맵)로 hash → 커밋 조회 O(1)
- 중복 방지: hash 생성 시 카운터+난수(또는 uuid) 등으로 세션 내 유일성 보장. 생성 전 기존 hash 집합과 비교해 겹치면 재생성하는 이중 장치가 있으면 더 좋음
- "왜 빠른가": dict 내부 해시 함수로 버킷 인덱스 계산 → 비교 대상 1개

- [ ] 통과

### Q9. 역색인(author/keyword)을 어떤 시점에, 어떤 방식으로 갱신하도록 설계했는가?

**모범답변 포인트**:
- 시점: **COMMIT이 만들어지는 순간 즉시 갱신**(쓰기 시점 인덱싱) → 검색 시점에는 계산 없이 바로 조회
- 방식: 메시지를 공백 split + 소문자 정규화한 토큰마다 `keyword → {commit_hash}` 목록에 추가, `author → {commit_hash}`도 동시 추가
- 대안 비교: 검색할 때마다 전체를 훑으며 인덱스를 만들면 매번 O(n) — 미리 만들어두면 검색이 O(1)

- [ ] 통과

### Q10. LOG, PATH, ANCESTORS에서 사용하는 그래프 탐색 로직을 어떻게 재사용 가능하게 구성했는가?

**모범답변 포인트**:
- algorithms.py에 공통 탐색 함수를 독립 구현: DFS 후위 순회(LOG의 위상 정렬 + ANCESTORS), BFS(PATH)
- 이웃(부모/자식)을 얻는 방법을 함수로 분리해두면 같은 탐색 골격을 여러 명령이 재사용
- "명령어마다 탐색을 따로 짜지 않았다"는 점이 핵심

- [ ] 통과

### Q11. 주요 함수/클래스에 docstring/주석을 어떤 기준으로 작성했는가?

**모범답변 포인트**: "무엇을 하는 함수인가(한 줄 요약) / 인자와 반환값 / 알고리즘 선택 이유(BFS인 이유 등)" 기준으로 썼다는 답이면 통과. 비전공자도 흐름을 따라올 수 있게 쓰라고 한 본인 규칙과 일치하는지도 함께 확인.

## 그룹 3. 원리 이해 · 근거 설명

### Q12. 커밋 그래프가 왜 DAG여야 하는지, 사이클이 생기면 어떤 문제가 발생하는가?

**모범답변 포인트**:
- 부모는 항상 과거의 커밋 → 시간이 뒤로 가는 간선이 존재할 수 없으므로 자연히 사이클 없는 방향 그래프(DAG)
- 사이클이 생기면: (1) LOG의 "부모 먼저" 순서 자체가 성립 불가(위상 정렬 존재하지 않음), (2) ANCESTORS/PATH 탐색이 무한 반복 위험(방문 체크 없다면), (3) "조상" 정의가 모호해짐

- [ ] 통과

### Q13. LOG의 "부모가 먼저" 조건을 만족시키기 위해 어떤 접근(위상 정렬 성격의 출력)을 적용했는가?

**모범답변 포인트**:
- DFS **후위 순회**: 자식에서 출발해 부모들을 먼저 다 방문하고 끝나는 순서를 활용하면 부모가 자식보다 앞에 놓이는 순서를 보장
- 또는 "아직 부모가 남은 커밋은 출력 보류"(Kahn 방식)로도 가능 — 어느 쪽이든 위상 정렬 개념을 말하면 통과
- 정렬 옵션(--sort-by)은 이 순서 위에서 merge sort로 재정렬하는 관계까지 말하면 좋음

- [ ] 통과

### Q14. PATH의 최단 경로에 어떤 알고리즘(BFS)을 선택했고, 간선을 무방향으로 정의한 이유는 무엇인가?

**모범답변 포인트**:
- 간선에 가중치가 없고 "몇 번 건너갔는가"가 최단 기준 → **BFS가 최초 도달 = 최단 경로**를 보장. 다익스트라 같은 가중치 알고리즘은 불필요
- 무방향 근거: 자식→부모만 간선을 허용하면 분기한 형제 커밋끼리는 서로 도달 불가. 공통 조상을 거쳐 "거꾸로 올라갔다 내려오는" 이동을 허용하려면 양방향으로 봐야 함
- 동률 경로 중 사전순 최소를 고르는 구현(예: target에서 BFS로 거리를 계산해두고 거리가 줄어드는 이웃 중 hash가 가장 작은 것 선택)까지 설명하면 만점

- [ ] 통과

### Q15. 정렬 알고리즘의 평균/최악 시간복잡도와 안정 정렬 여부를 설명할 수 있는가?

**모범답변 포인트** (merge sort 기준):
- 평균 O(n log n), **최악도 O(n log n)** (퀵소트는 최악 O(n²))
- 안정 정렬 O: 값이 같은 원소의 원래 순서가 보존됨. 병합 시 왼쪽 배열을 먼저 취하기 때문
- 왜 안정이 중요한가: LOG --sort-by=author에서 같은 author끼리는 기존(위상) 순서가 유지됨

- [ ] 통과

### Q16. 역색인이 순회 검색보다 빠른 이유를 자료구조/시간복잡도 관점에서 설명할 수 있는가?

**모범답변 포인트**:
- 순회 검색: 검색할 때마다 모든 커밋 메시지를 훑음 — O(n)
- 역색인: 단어별 목록장이 이미 존재 → 해시 조회 1번 + 해당 커밋 목록 반환 — O(1) + 결과 크기
- 본질은 **비용을 검색 시점에서 커밋 생성 시점으로 옮긴 것**(전처리). 커밋이 자주 검색되고 수정이 드물수록 유리

- [ ] 통과

## 그룹 4. 확장 · 응용 질문

### Q17. 커밋 수가 10배 늘어났을 때 병목이 될 지점을 예측하고, 개선 방향(자료구조/알고리즘)을 설명할 수 있는가?

**모범답변 포인트**:
- LOG: 매번 전체 그래프 위상 정렬 → O(V+E). 개선: 최근 N개만 보는 창 제한, 증가분만 정렬하는 캐시
- SEARCH는 역색인 덕분에 영향 적음(결과 목록만 커짐) — 구조적 강점을 인식하는지 확인
- PATH/ANCESTORS: BFS/DFS도 O(V+E)라 커지지만, 실사용은 국소 범위라 괜찮다는 식의 판단이 있으면 좋음
- 해시 충돌/메모리: dict 확장 비용은 상각 O(1)로 흡수 가능

- [ ] 통과

### Q18. PATH의 간선 정의를 "부모 방향만 허용"으로 바꾸면 결과가 어떻게 달라지고, 구현은 무엇을 바꿔야 하는가?

**모범답변 포인트**:
- 결과 변화: 자식→부모 방향으로만 갈 수 있으므로, **한 커밋이 다른 커밋의 조상인 경우에만** 경로 존재. 분기한 형제 커밋끼리는 공통 조상이 있어도 `No path`
- 구현 변경: BFS의 이웃 생성 함수에서 자식 방향(역방향 간선)을 빼고 parents만 반환하면 끝 — 이웃 로직이 함수로 분리돼 있어 수정이 국소적이라는 점이 포인트

- [ ] 통과

### Q19. LOG --sort-by=author 요구사항이 "부모-자식 선후도 유지"로 강화되면 어떤 전략으로 해결할 것인가?

**모범답변 포인트**:
- 핵심: **안정 정렬 + 올바른 기준 순서**의 조합
- 전략: (1) 위상 정렬로 "부모 먼저" 기본 순서를 만든 뒤, (2) 안정적인 merge sort로 author 기준 재정렬 → 같은 author끼리는 원래 위상 순서가 보존됨. 하지만 서로 다른 author 간에는 부모-자식이 깨질 수 있으므로, 완전 보장이 필요하면 정렬 키를 (author, 위상순서) 처럼 복합 키로 설계
- "안정 정렬이 왜 필요한가"를 스스로 연결해서 설명하면 만점

- [ ] 통과

### Q20. 해시 생성 방식을 카운터 기반 ↔ 난수 기반으로 바꿀 때 테스트/재현성/디버깅에 미치는 영향은?

**모범답변 포인트**:
- 카운터 기반: hash가 실행마다 동일 → 테스트 예상값 고정 가능, 재현·디버깅 쉬움. 단 규칙이 노출되고 세션 간 중복 관리 필요
- 난수 기반: 충돌 확률적으로 안전, 실제 git과 비슷. 하지만 실행마다 달라져 테스트가 hash 값을 하드코딩 못 함 → "hash를 직접 받는 명령(PATH, ANCESTORS)" 테스트는 LOG 출력에서 hash를 읽어 넘기는 간접 방식으로 바꿔야 함
- 디버깅: 카운터는 "3번째 커밋이 문제" 식 추적이 쉬움. 난수는 로그 기록이 없으면 같은 커밋을 다시 찾기 어려움

- [ ] 통과
