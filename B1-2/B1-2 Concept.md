# 수행 목적

README를 보면 이 미션은 `agent-app-leak`라는 프로그램을 Docker 안에서 실행하고, `MEMORY_LIMIT`, `CPU_MAX_OCCUPY`, `MULTI_THREAD_ENABLE` 같은 환경변수를 조절하면서 장애가 어떻게 드러나는지 관찰하는 실험입니다.

메모리 누수는 `MemoryWorker`가 약 3초마다 Heap을 25MB씩 계속 증가시키는 방식으로 나타납니다.

```
25MB -> 50MB -> 75MB -> 100MB -> ...
```

중요한 점은 **증가만 있고 감소가 없다**는 것입니다. 로그에 `free`, `release`, `cleanup`, `GC` 같은 메모리 해제 흔적이 없고, Heap이 일정한 간격으로 계속 커집니다. 그래서 원인은 **"반복 작업 중 메모리를 할당하지만 해제하지 않는 구조"**라고 볼 수 있습니다.

`MEMORY_LIMIT=100MB`일 때는 약 100MB에 도달하자 `MemoryGuard`가 프로세스를 강제 종료합니다. 이후 `MEMORY_LIMIT=256MB`로 올리면 프로그램은 더 오래 살아 있지만, 결국 275MB 근처에서 다시 종료됩니다. 즉, **제한값을 올리면 생존 시간은 늘어나지만 누수 자체가 해결되지는 않습니다**.

여기서 알 수 있는 것은 다음과 같습니다.

- **메모리 제한은 누수를 고치는 기능이 아니라 피해를 막는 보호 장치입니다.**
- **제한값을 올렸는데도 같은 속도로 메모리가 증가하면 근본 원인은 그대로입니다.**
- **Heap 증가 패턴을 보면 누수가 일시적 증가인지, 지속적 누수인지 구분할 수 있습니다.**
- **`MEMORY_LIMIT`은 시스템 전체가 불안정해지기 전에 문제 프로세스를 멈추게 하는 안전선입니다.**

CPU 제한 쪽은 메모리와 조금 다릅니다. `CPU_MAX_OCCUPY=30%`로 낮추면 CPU 사용량이 점점 올라가다가 30%에 도달했을 때 프로세스가 죽는 것이 아니라 `cooldown`에 들어갑니다.

```
CPU 상승 -> 30% 도달 -> Peak reached -> cooldown -> 다시 상승
```

즉 **CPU 제한은 이 프로그램에서는 "강제 종료 조건"이 아니라 "부하 조절 조건"**처럼 동작합니다. CPU를 너무 많이 쓰면 잠시 쉬게 만들고, 다시 낮아지면 작업을 재개합니다.

그래서 CPU 범위를 제한하면서 알 수 있는 것은 다음과 같습니다.

- CPU 과점유는 반드시 프로세스 종료로 이어지는 문제가 아닐 수 있습니다.
- CPU 제한은 시스템 안정성을 위해 부하를 조절하는 역할을 합니다.
- 제한값이 낮을수록 cooldown이 자주 발생하고, 처리량은 줄어들 수 있습니다.
- 제한값이 높을수록 성능은 좋아질 수 있지만, 다른 프로세스에 줄 수 있는 영향도 커집니다.

**이 미션의 목적은 단순히 프로그램을 실행해보는 것이 아니라, 장애를 "증상 → 증거 → 원인 → 조치" 흐름으로 분석하는 연습입니다.**

# 기초 개념

## 1. 프로그램 (Program) vs 프로세스 (Process) vs 메모리 (Memory)

### 프로그램 (Program)
- **정의**: 하드디스크나 SSD 등 저장장치에 파일 형태로 저장된 **정적인 상태의 명령어 모음**입니다.
- **비유**: 실행되기 전의 **레시피 북** 또는 **설계도**와 같습니다.
- **특징**: 생명력이 없으며, 전원이 꺼져도 사라지지 않는 비휘발성 데이터입니다.

### 프로세스 (Process)
- **정의**: 메모리에 적재되어 CPU에 의해 실행 중인 **동적인 상태의 프로그램**을 말합니다.
- **비유**: 설계도를 보고 실제로 공장에서 제품을 **생산 중인 상태**입니다.
- **특징**: 
  - CPU 스케줄링의 대상이 되며, 운영체제(OS)로부터 독립된 메모리 공간을 할당받습니다.
  - 고유한 PID(Process ID)를 가집니다.
  - 각 프로세스는 자신만의 메모리 공간을 독립적으로 보유합니다.

### 메모리 (Memory)
- **정의**: CPU가 즉각적으로 접근할 수 있도록 실행 중인 프로그램과 데이터를 임시 저장하는 공간(RAM)입니다.
- **역할**: CPU와 보조기억장치(SSD/HDD) 사이의 거대한 속도 차이를 메워주는 완충 지대입니다.

### 프로세스 메모리 구조
![메모리 구조](/Codyssey-B1/B1-2/test/screenshot/memory_structure_segments.png)

메모리에 로드된 프로세스는 다음과 같이 방을 나누어 씁니다:

```
높은 주소
┌─────────────────────────┐
│         Stack           │ ← 5층: 함수 호출 기록, 지역변수
│    (아래로 성장 ↓)         │   (자동 관리 - 함수 끝나면 사라짐)
├─────────────────────────┤
│           ↕             │ ← 빈 공간 (Stack ↔ Heap이 서로 마주보며 성장)
├─────────────────────────┤
│          Heap           │ ← 4층: 동적 할당 공간 **누수 발생 지점!**
│    (위로 성장 ↑)          │   (수동 관리 - 개발자가 직접 해제해야 함)
├─────────────────────────┤
│          BSS            │ ← 3층: 초기화 안 된 전역변수
├─────────────────────────┤
│          Data           │ ← 2층: 초기화된 전역변수
├─────────────────────────┤
│          Text           │ ← 1층: 실행 코드 자체
└─────────────────────────┘
낮은 주소
```

> **이 미션의 누수는 4층(Heap)에서 발생!**  
> 짐을 계속 쌓기만 하고 치우지 않아서 아파트가 꽉 찬 상황

## 2. 스레드 (Thread) vs 프로세스 (Process)

### 정의

**프로세스:** 운영체제로부터 자원을 할당받은 **작업**의 단위

**스레드:** 프로세스가 할당받은 자원을 이용하는 **실행 흐름**의 단위

**프로그램 → 프로세스 → 스레드**
![스레드](/Codyssey-B1/B1-2/test/screenshot/process_execution_flow.png)
### 스레드의 필요성

과거에는 프로그램을 실행할 때 실행 시작부터 실행 끝까지 프로세스 하나만을 사용해서 진행했습니다. 하지만 시간이 흐를수록 프로그램이 복잡해지고 프로세스 하나만을 사용해서 프로그램을 실행하기는 벅차게 되었습니다.

한 가지 접근은 "한 프로그램을 처리하기 위한 프로세스를 여러 개 만들면 되지 않을까?" 하는 것이었지만, 이는 불가능합니다. 왜냐하면 운영체제는 안전성을 위해서 프로세스마다 자신에게 할당된 메모리 내의 정보에만 접근할 수 있도록 제약을 두고 있기 때문입니다.

아무튼 **프로세스와는 다르게 스레드 간 메모리를 공유하며 작동**하는 더 작은 실행 단위 개념이 필요하게 되었습니다. 이 개념이 바로 **스레드**입니다.

스레드끼리 프로세스의 자원을 공유하면서 프로세스 실행 흐름의 일부가 되는 것입니다. 프로그램이 코드 덩어리라고 했을 때, 스레드는 코드 내에 선언된 함수들이 되고 따라서 main 함수 또한 일종의 스레드라고 볼 수 있게 됩니다.

### 프로세스 vs 스레드

```
프로세스 (Process):
- 독립적인 프로그램 실행 단위
- 각자 메모리 공간 보유 (격리됨)
- 예: 크롬, 유튜브, 카톡 앱

스레드 (Thread):
- 같은 프로세스 내의 실행 단위
- 메모리 공간 공유
- 예: 크롬 내의 여러 탭들이 동시에 작동

우리 테스트:
agent-leak-app 프로세스 내에
├─ Worker-Thread-1
├─ Worker-Thread-2
└─ (다른 스레드들)
이 동시에 실행
```

### 비유: 식당으로 이해하기

```
프로세스 = 식당 전체
┌─────────────────────────────────┐
│           식당 (Process)         │
│  ┌──────┐ ┌──────┐ ┌──────┐   │
│  │웨이터1│ │웨이터2│ │웨이터3│   │ ← 스레드들
│  │Thread│ │Thread│ │Thread│   │
│  └──────┘ └──────┘ └──────┘   │
│                                 │
│  [공유 주방 = 공유 메모리(Heap)] │ ← 모든 스레드가 같은 Heap 사용!
└─────────────────────────────────┘
```

**싱글 스레드 식당**: 직원이 1명입니다. 요리, 서빙, 계산을 순서대로 혼자 다 해야 하므로 손님이 밀리면 느려집니다.

**멀티 스레드 식당**: 직원이 3명(스레드 3개)입니다. 1명은 요리, 1명은 서빙, 1명은 계산을 **동시에** 처리하여 식당이 효율적으로 돌아갑니다. 이 직원들은 식당의 주방(메모리 공간)을 공유합니다.

> **B1-2의 위험 포인트**  
> `MULTI_THREAD_ENABLE=True` 상태에서  
> 여러 스레드가 **같은 Heap**에 동시 접근  
> → 메모리 누수가 더 빠르게 진행될 수 있음

# 개념 1: OOM (Out of Memory)

## 메모리 누수 (Memory Leak)

### 비유: 욕조에 물을 받는데 마개를 안 뽑는 것

```
정상적인 메모리 사용:          메모리 누수:

malloc() → 할당            malloc() → 할당 
사용...                    사용...
free()   → 해제            free() 없음! 

[물 받고 → 빼고 → 반복]        [물 받고 → 받고 → 받고 → 넘침!]
```

### 코드로 보는 차이

```c
//  정상: 할당 후 해제
void 정상함수() {
    char* data = malloc(25MB);  // 할당
    // ... 사용 ...
    free(data);                 // ← 반드시 해제!
}

//  누수: 해제 없음
void 누수함수() {
    char* data = malloc(25MB);  // 할당
    // ... 사용 ...
    // free(data); ← 이게 없음!
}   // 함수 끝나도 메모리는 그대로 점유 중
```

### 이 미션에서의 패턴

```
T+2초:  malloc(25MB)  free 없음 → 25MB 점유
T+5초:  malloc(25MB)  free 없음 → 50MB 점유
T+8초:  malloc(25MB)  free 없음 → 75MB 점유
T+11초: malloc(25MB)  free 없음 → 100MB 점유 → 종료

추정되는 내부 동작 (의사 코드):
def memory_worker():
    while True:
        data = allocate(25 * MB)  # 할당
        # free(data) ← 이게 없음!
        time.sleep(3)             # 3초 대기
```

### 정상적인 코드의 메모리 패턴

> **정상적인 코드의 경우 메모리의 Heap이 일시적으로 상승했다가 가비지 컬렉션에 의해서 자동으로 떨어진다.**  
> **현재의 경우 HEAP의 메모리가 계속해서 우상향한다. 초기 메모리 상태로 되돌아오거나 떨어지지 않는다.**

## 가비지 컬렉션 (Garbage Collection)
![가비지컬렉션](/Codyssey-B1/B1-2/test/screenshot/garbage_collection_works.png)
### 비유: 자동 청소부 vs 수동 청소

```
언어별 메모리 관리 방식:

C/C++ (수동)                Python/Java (자동 GC)
개발자가 직접 청소           청소부(GC)가 알아서 청소

malloc() → 할당             new Object() → 할당
...사용...                  ...사용...
free()   → 해제          // 자동으로 해제됨 🤖
          ↑
       잊으면 누수!
```

> **가비지 컬렉션**은 자바의 메모리 관리 방법 중의 하나로 JVM(자바 가상 머신)의 Heap 영역에서 동적으로 **할당했던 메모리 중 필요 없게 된 메모리 객체(garbage)를 모아 주기적으로 제거하는 프로세스**를 말합니다.

### GC가 있어도 누수가 생기는 경우

```python
# Python에서도 누수 가능한 패턴!
cache = []  # 전역 리스트

def 문제있는함수():
    data = [0] * (25 * 1024 * 1024)  # 25MB
    cache.append(data)  # 전역에 추가
    # GC가 있어도 cache가 참조 중이라 해제 못 함!
    # → 참조가 남아있으면 GC도 수거 불가
```

> **GC의 한계**: 참조(Reference)가 남아있으면 수거 불가  
> → 이 미션에서 "가비지 컬렉션 개선" 권장사항이 나온 이유

## OOM (Out of Memory)

### 비유: 주차장이 꽉 찬 상황

> 주차장(메모리)이 꽉 찼는데 새 차(프로세스)가 들어오려 함  
> → 관리인(OS)이 강제로 차를 견인(프로세스 종료)

```
OOM 발생 흐름:

메모리 요청
    │
    ▼
사용 가능한 메모리 있음? ──YES──→ 할당 성공 
    │
    NO
    │
    ▼
스왑(Swap) 공간 있음? ──YES──→ 스왑 사용 (느려짐)
    │
    NO
    │
    ▼
OOM Killer 발동! 
    │
    ▼
희생 프로세스 선택 → SIGKILL 전송 → 강제 종료
```

### Linux OOM Killer vs MemoryGuard

| 구분 | Linux OOM Killer | MemoryGuard (이 미션) |
|------|-----------------|----------------------|
| **주체** | OS 커널 | 애플리케이션 자체 |
| **발동 조건** | 시스템 전체 메모리 부족 | 프로세스 한계치 도달 |
| **목적** | 시스템 보호 | 프로세스 자기 보호 |
| **신호** | SIGKILL | SIGKILL (자기 자신에게) |

### 메모리 보호 정책들

#### OOM Killer (Out of Memory Killer)

시스템의 **실제 물리 메모리와 스왑(Swap) 공간이 모두 고갈**되어 가동이 불가능할 때, OS 전체가 다운되는 최악의 상황을 막기 위해 가동하는 **최후의 보루**입니다.

#### 메모리 가드 (Memory Guard)

소프트웨어 공학 및 보안 관점에서 말하는 '메모리 가드'는 프로그램이 허용되지 않은 메모리 영역을 침범해 시스템이 오염되는 것을 막는 **경계선 역할**을 합니다.

## 선형 증가 패턴 분석

### 이 미션에서 관찰되는 패턴의 의미

```
메모리(MB)
100 |                    ●  ← 종료
 75 |               ●
 50 |          ●
 25 |     ●
  0 +----+----+----+----+
    0    3    6    9   (초)

기울기 = 25MB / 3초 ≈ 8.3MB/초
→ 일정한 기울기 = 규칙적인 누수
→ 랜덤하지 않음 = 의도된 동작 or 반복 루프
```

> **패턴으로 알 수 있는 것**
> - **랜덤 누수**: 불규칙한 증가 → 버그성 누수
> - **선형 누수 (이 경우)**: 규칙적 증가 → 반복 루프에서 해제 없이 할당

# 개념 2: CPU 분석

## CPU 스케줄링 (CPU Scheduling)

**정의**: 여러 프로세스가 CPU를 공유할 때, 어떤 프로세스가 언제 CPU를 사용할지 결정하는 것

### 현실적 예시

```
1초 동안 4개의 프로세스가 있다면:
- Process A: 0.0 ~ 0.25초 CPU 사용
- Process B: 0.25 ~ 0.5초 CPU 사용
- Process C: 0.5 ~ 0.75초 CPU 사용
- Process D: 0.75 ~ 1.0초 CPU 사용

→ OS가 프로세스들을 번갈아가며 실행
```

### 우리 테스트에서

```
CpuWorker가 5% ~ 30% CPU 사용
= OS가 CpuWorker에게 CPU 시간을 일부 할당
= 나머지 CPU는 다른 프로세스에 할당
```

## CPU 사용률 (CPU Utilization)

**정의**: CPU가 실제로 작업하는 시간의 비율

### 계산

```
CPU 사용률 = (실제 작업 시간 / 총 시간) × 100%

예:
- 1초 동안 0.3초 작업 → 30% CPU 사용률
- 1초 동안 0.05초 작업 → 5% CPU 사용률
```

### 로그에서 보이는 것

```
2026-05-27 05:58:52,265 [INFO] [CpuWorker] Current Load: 5.00%
→ 지난 1초 동안 CPU를 5% 사용했다는 뜻
```

## CPU 한계 (CPU Limit / Threshold)

**정의**: 특정 프로세스가 사용할 수 있는 최대 CPU 비율

### 우리 테스트

```
CPU_MAX_OCCUPY=30%
= CpuWorker는 최대 30%까지만 CPU 사용 가능
= 30%를 초과하면 제한됨
```

### 현실적 예시

```
컴퓨터 CPU가 100% 능력이라고 하면:
- 이 프로세스: 최대 30까지만 사용
- 다른 프로세스들: 나머지 70을 나눠 씀
```

## Throttling (스로틀링 / 조절)

**정의**: CPU 사용을 의도적으로 줄이는 행위

### 우리 로그에서

```
2026-05-27 05:59:12,998 [INFO] [CpuWorker] Peak reached (30.00%). Starting cooldown...
```

→ CPU가 30%에 도달하자 CPU 사용을 줄임 (throttle)

### 실생활 예시

```
- 노트북 배터리 부족 → CPU 속도 낮춤
- 폰 발열 높음 → CPU 성능 제한
- 서버 부하 높음 → 특정 서비스 속도 제한
```

## Cooldown (쿨다운 / 회복 시간)

**정의**: 과부하 상태에서 벗어나기 위해 대기하는 기간

### 우리 테스트에서

```
Phase 1: CPU 상승 (5% → 30%)
         ↓
Phase 2: Cooldown 시작 (Peak reached)
         CPU를 30% → 5%로 낮춤
         약 16초 소요
         ↓
Phase 3: Cooldown 완료 (5%)
         다시 상승 시작
```

### 시간대

```
05:59:12 - Cooldown 시작
05:59:28 - Cooldown 완료 (약 16초)
```

## Workload (워크로드)

**정의**: 프로세스가 해야 할 일의 양 또는 강도

### 우리 테스트

```
CpuWorker의 워크로드:
- 초기: 낮음 (5% CPU만 사용)
- 중간: 증가 (점점 더 많은 계산)
- 최고: 30% (최대 허용치)
- 쿨다운: 낮춤 (의도적으로 일을 줄임)
```

## 스레드 스케줄링 심화

### 비선점형 스케줄링 (Non-preemptive Scheduling)

스레드가 스스로 CPU 제어권을 반납할 때까지 다른 스레드가 CPU를 강제로 빼앗을 수 없는 방식입니다.

- **특징**: 문맥 교환(Context Switch) 오버헤드가 적고 구현이 단순합니다.
- **단점**: 하나의 스레드가 긴 작업이나 무한 루프에 빠지면 시스템 전체가 멈출 수 있습니다.
- **적용 알고리즘**: FCFS, SJF, HRN 등

### 선점형 스케줄링 (Preemptive Scheduling)

OS가 우선순위나 할당 시간(Time Slice)을 기준으로 실행 중인 스레드를 강제로 중단시키고, 다른 스레드에 CPU를 할당하는 방식입니다.

- **특징**: 현대 OS(Windows, Linux, macOS 등)가 채택하는 주류 방식입니다. 시분할 시스템과 실시간 시스템에 적합합니다.
- **단점**: 잦은 문맥 교환으로 인해 시스템 오버헤드가 발생할 수 있습니다.
- **적용 알고리즘**: Round Robin, SRTF, 다단계 큐 등

# 🔵 개념 3: Deadlock (교착상태)

## 멀티스레드 환경 (Multithreading)

**정의**: 하나의 프로세스 내에서 여러 개의 스레드가 동시에 실행되는 것

### 멀티스레드 환경의 추가 위험

```
Thread 1: malloc(25MB) ──┐
Thread 2: malloc(25MB) ──┼──→ Heap 동시 접근
Thread 3: malloc(25MB) ──┘    (동기화 없으면 더 위험!)

경고 메시지가 나온 이유:
"POTENTIAL DEADLOCK IN CONCURRENT MODE"
→ 스레드들이 서로 자원을 기다리다 멈플 수 있음
```

## 자원 (Resource)

**정의**: 여러 스레드가 공유하는 데이터나 객체

### 우리 테스트의 자원

```
1. Shared_Memory_A (공유 메모리)
2. Socket_Pool_B (소켓 풀)

이 둘을 여러 스레드가 동시에 접근하려 함
```

### 현실적 예시

```
은행의 계좌 잔액 (자원):
- 스레드1: 입금 시도
- 스레드2: 출금 시도
→ 동시에 접근하면 일관성 깨짐
→ 따라서 한 번에 1개 스레드만 접근 가능
```

## 락 (Lock / Mutual Exclusion - 상호 배제)

**정의**: 한 번에 1개 스레드만 자원을 사용하도록 제한하는 메커니즘

### 동작

```
Lock 획득:
스레드1: "Shared_Memory_A 사용하겠습니다" (Lock 획득 ✓)
스레드2: "Shared_Memory_A 사용하겠습니다" (Lock 대기... ⏳)

스레드1이 작업 완료:
스레드1: "다 했습니다" (Lock 해제)
스레드2: "이제 사용합니다" (Lock 획득 ✓)
```

### 로그에서 확인

```
2026-05-27 05:50:08,816 [INFO] LOCK ACQUIRED: [Shared_Memory_A]
→ 이 스레드가 락을 획득함
→ 다른 스레드는 접근 불가
```

## 교착상태 (Deadlock)

**정의**: 2개 이상의 스레드가 서로가 가진 자원을 기다리며 무한히 대기하는 상태

### 비유: 좁은 골목에서 마주친 두 차

```
Thread A가 가진 것: 자원 🔑1
Thread A가 필요한 것: 자원 🔑2

Thread B가 가진 것: 자원 🔑2
Thread B가 필요한 것: 자원 🔑1

결과:
Thread A: "🔑2 줘!" → Thread B: "🔑1 먼저 줘!"
Thread B: "🔑1 줘!" → Thread A: "🔑2 먼저 줘!"

→ 둘 다 영원히 대기... 💀 데드락!
```

### 우리 테스트의 상황

```
시간순서:
T1: 스레드1이 자원A 획득
    스레드2가 자원B 획득

T2: 스레드1이 자원B 필요 → 스레드2가 가지고 있음 → 대기
    스레드2가 자원A 필요 → 스레드1이 가지고 있음 → 대기

T3: 둘 다 자신이 필요한 자원을 못 가지고 있음
    → 영원히 대기 (교착상태)

로그:
2026-05-27 05:50:10,820 [INFO] WAITING for [Socket_Pool_B]... (Status: BLOCKED)
2026-05-27 05:50:10,820 [INFO] WAITING for [Shared_Memory_A]... (Status: BLOCKED)
→ 둘 다 BLOCKED 상태에서 멈춤
```

### 현실적 예시: 식사하는 철학자 문제

```
철학자 A, B가 앉아있고 포크 2개가 있음
(A 왼쪽에 포크1, 오른쪽에 포크2, B 오른쪽에 포크1... 등)

A: 왼쪽 포크 집음 (포크1 획득)
B: 오른쪽 포크 집음 (포크2 획득)

A: 오른쪽 포크 필요 → B가 가지고 있음 (대기)
B: 왼쪽 포크 필요 → A가 가지고 있음 (대기)

→ 둘 다 영원히 기다림 (밥을 못 먹음)
```

## 데드락 발생 4가지 필수 조건

데드락이 발생하려면 **다음 4가지 조건을 모두 만족**해야 합니다:

### 조건 1: 상호 배제 (Mutual Exclusion)

```
자원이 배타적으로 사용됨
= 한 번에 1개 스레드만 사용 가능

우리 경우:
Shared_Memory_A는 한 번에 1개 스레드만 접근 가능
Socket_Pool_B도 한 번에 1개 스레드만 접근 가능

✓ 만족
```

### 조건 2: 점유 대기 (Hold and Wait)

```
스레드가 자원을 보유하면서 다른 자원 대기
= 가진 것 놓지 않고 필요한 것 기다림

우리 경우:
스레드1: 자원A 보유 → 자원B 대기
스레드2: 자원B 보유 → 자원A 대기

✓ 만족
```

### 조건 3: 비선점 (No Preemption)

```
자원을 강제로 빼앗을 수 없음
= 획득한 스레드만 해제 가능

우리 경우:
스레드1이 자원A를 가지면
다른 스레드가 강제로 빼앗을 수 없음
(스레드1이 해제할 때까지 대기)

✓ 만족
```

### 조건 4: 순환 대기 (Circular Wait)

```
자원 대기가 순환 구조를 이룸
= A → B → A 형태 (또는 A → B → C → A 등)

우리 경우:
스레드1 (자원A 보유) → 스레드2 (자원B 보유) → 스레드1
                    ↑                              ↓
                    └──────────────────────────────┘

순환 구조!

✓ 만족
```

**결론**: 4가지 조건 모두 만족 → **데드락 발생**

## 자원 획득 순서 (Resource Ordering)

**정의**: 여러 자원을 사용할 때 획득하는 순서

### 문제 상황 (우리 테스트)

```
스레드1: 자원A → 자원B 순서로 획득
스레드2: 자원B → 자원A 순서로 획득
                 ↑
                다른 순서!
```

### 해결책

```
모든 스레드가 동일 순서로 획득:

방법1:
스레드1: 자원A → 자원B
스레드2: 자원A → 자원B (동일 순서)

방법2:
스레드1: 자원B → 자원A
스레드2: 자원B → 자원A (동일 순서)

→ 순환 대기 불가능!
```

## 블로킹 (Blocking) vs 대기 (Waiting)

### 블로킹 (Blocking)

```
스레드가 자원을 기다리며 실행을 멈춤

로그에서:
[INFO] WAITING for [Socket_Pool_B]... (Status: BLOCKED)
→ BLOCKED 상태 = 실행하지 않음, 기다리는 중
```

### BLOCKED 상태의 CPU/메모리 상태

```
BLOCKED 상태의 스레드:
- CPU: 0% (실행하지 않음)
- 메모리: 변화 없음 (새로 할당 안 함)
- 로그: 안 나옴 (I/O 수행 안 함)
```

### 테스트 결과

```
2026-05-27 05:50:10,820 이후:
- CPU: 0%
- 메모리: 정체
- 로그: 없음
→ 모든 스레드가 BLOCKED 상태
```

## 시그널 (Signal) - SIGKILL (강제종료)

### 비유: 프로세스에게 보내는 메시지

```
Signal 종류:
┌──────────┬──────────────────────────────────────────┐
│ SIGTERM  │ "정리하고 종료해줘" (부드러운 요청)        │
│ SIGKILL  │ "즉시 종료!" (거부 불가, OS가 강제 실행)   │
│ SIGINT   │ "Ctrl+C" (인터럽트)                       │
│ SIGSEGV  │ "잘못된 메모리 접근!" (세그폴트)           │
└──────────┴──────────────────────────────────────────┘

이 미션:
MemoryGuard → SIGKILL → 프로세스 ID 강제 종료
                ↑
         핸들러 등록 불가
         = 프로세스가 막을 방법 없음
```

## 🎯 실제 시험에 나올 개념들

### CPU 관련

1. **CPU 스케줄링**: 여러 프로세스가 CPU를 공유하는 방식
2. **CPU 사용률**: (실제 작업시간 / 총시간) × 100%
3. **Throttling**: CPU 사용을 의도적으로 제한
4. **Cooldown**: 과부하에서 벗어나기 위한 회복 기간
5. **Workload**: 프로세스가 해야 할 일의 양

### Deadlock 관련

1. **Multithreading**: 하나의 프로세스 내 여러 스레드 동시 실행
2. **자원**: 여러 스레드가 공유하는 데이터/객체
3. **락(Lock)**: 한 번에 1개 스레드만 접근하도록 제한
4. **Deadlock**: 2개 이상 스레드가 서로의 자원을 무한히 기다리는 상태
5. **데드락 4가지 조건**: Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait
6. **자원 획득 순서**: 모든 스레드가 동일 순서로 자원 획득

# 평가 기준

## 평가항목 1: 기술적 증거 (Technical Evidence)

### 목표: 3가지 장애를 로그로 재현하고 환경변수 조정 전후 비교

#### OOM 요구사항
- [ ] 메모리 사용량이 선형적으로 증가하다가 프로세스가 강제 종료되는 패턴이 로그에 기록되어 있는가?
- [ ] 환경변수(MEMORY_LIMIT) 조정 후 프로세스 생존 시간이 늘어난 Before & After 비교 결과가 있는가?

#### CPU 요구사항
- [ ] CPU 사용률이 임계치를 초과하여 프로세스가 종료되는 패턴이 로그에 기록되어 있는가?
- [ ] 환경변수(CPU_MAX_OCCUPY) 조정 후 프로세스 종료 여부/생존 시간이 변화한 Before & After 비교 결과가 있는가?

> 예시 개선사항:

#### 우선순위 판단

- [ ] 이번 미션에서 겪은 3가지 장애(OOM, CPU Spike, Deadlock) 중 실제 서비스 환경에서 가장 치명적인 것은 무엇이라고 생각하는가? 그 이유와 함께, 해당 장애를 근본적으로 예방하는 방법을 제안할 수 있는가?

| 장애 | 영향 범위 | 복구 시간 | 심각도 | 예방 방법 |
|------|---------|---------|--------|---------|
| **OOM** | 단일 프로세스 | 수초 | 높음 | 메모리 누수 코드 리뷰, GC 튜닝 |
| **CPU** | 시스템 전체 | 수분 | 중간 | CPU 제한, 로드 밸런싱 |
| **Deadlock** | 전체 서비스 | 수시간 | **매우 높음** | 자원 순서 정의, 타임아웃 설정 |

> **Deadlock이 가장 치명적인 이유:**
> - 자동 복구 불가능 (강제 재시작 필요)
> - 사용자에게 완전한 서비스 거부
> - 감지까지의 시간이 최장

#### 트러블슈팅 우선순위

- [ ] 만약 동일한 서버에서 OOM과 Deadlock이 동시에 발생했다면, 어떤 순서로 트러블슈팅을 진행하겠는가? 우선순위 판단의 근거를 설명할 수 있는가?


# 📝 최종 요약

## OOM (01번)

```
MemoryWorker가 3초마다 25MB 할당
→ free 없음 → 메모리 누수
→ Heap이 선형으로 증가 (25MB/3초)
→ MEMORY_LIMIT 도달
→ MemoryGuard 발동 → SIGKILL
→ 프로세스 강제 종료

결론: 메모리 누수는 강제 종료로만 제어 가능
     → 근본 원인은 코드에서 수정해야 함
```

## CPU (02번)

```
CpuWorker가 부하를 계속 증가시킴
→ 30%에 도달하면 "Peak reached"
→ Cooldown 시작 (부하 자동 감소)
→ 5%까지 내려가면 "Cooldown complete"
→ 다시 부하 증가
→ 반복 (무한 사이클)

결론: CPU 정상 작동, 자동 조절 메커니즘 우수
```

## Deadlock (03번)

```
스레드1: 자원A 획득 → 자원B 대기
스레드2: 자원B 획득 → 자원A 대기

→ 서로의 자원을 무한히 기다림
→ 4가지 데드락 조건 모두 만족
→ 프로세스 멈춤 (응답 불가)
→ 강제 재시작만이 유일한 방법

결론: 위험! 즉시 MULTI_THREAD=false로 전환 필요
```
